# What gslides.py check and lint.py do

Open when you read the output of `gslides.py check` or `slides.py lint`, or when deciding whether a `要確認` may stay.

## What gslides.py check does

1. Writes the `presentations.get` JSON to `/tmp/slides_<first 8 chars of the ID>/deck.json`
2. Writes the text and notes of each page to `deck.md` (the text you pass to reviews)
3. Runs `lint.py` (below) on the JSON
4. Takes images (Google-rendered thumbnails, 1600 × 900) of pages changed since the last run into `p-NN.webp` (6 in parallel. Waits before 60 per minute. The API returns PNG only; `sheet.py --webp` turns it into lossless WebP, the same pixels in about 40% of the bytes, because every image read stays in the conversation and the request has a 32 MB limit. Without uv or Pillow, the pages taken in that run get no image (`image` is null in `changed.json`; lint, `deck.md`, and `changed.json` still come out) and the next check takes them again, because one folder never mixes PNG and WebP). Pages are identified by objectId (`slides.py build` creates only pages whose content changed, with new IDs, so the same ID means the same content). Other pages keep their previous images; images whose page number shifted are moved (only the page number at the bottom right is old). If someone edited in the UI after the last build, all pages. `--all` for all pages, `--pages 3,5` for only those pages
5. `box_pad.py` measures, on the images it took (laying out each page), the gap between top-aligned text of 2 or more lines inside a filled box and the bottom edge of the box, and reports gaps narrower than one character as 「要確認（画像で測った）」 (`deck-design` → slides §4. Line height cannot be estimated from the JSON, so it is measured on images. 2026-10-09). For text right above the bottom edge of a white card, it checks for one character even for a 1-line tag (such as 「2 回まで」) (2026-10-14). It also reports top-aligned text in a single standalone light panel where the space below is 0.25 in or more larger than the space above (center it or shrink the panel. 2026-10-10)

6. Writes the page numbers it took, the image paths, and that page's lint and box_pad findings to `changed.json` (`slides.py build` also writes the pages it rebuilt to the same file). Prints the seconds per step and the 429 waits on one line to standard error (build does too)

If the lint has `要修正`, it returns exit 1 after taking the images.

## What lint.py does

Written rules are easy to break, so whatever a machine can check is counted here (standard library only. It also runs alone as `python3 lint.py <deck.json>`). The content and sources of the rules are in `deck-writing` and `deck-design`. Theme colors are resolved to actual colors with the deck master's color scheme.

- **List of headings:** Prints the largest text on each page in order, with the lead indented below it if there is one. If it likely does not fit on one line, it adds 「2 行の見込み」. Read it through and check that the story holds (`deck-writing` → content).
- **Body character count:** Prints, per page, the number of characters excluding the heading, lead, source line, and footer. With `--talk` (talks such as LTs), it reports pages over 125 characters as `要確認` (`deck-writing` → content §2).
- **`要修正` (exit 1):** emoji, long dashes (—), leftover placeholders (TODO, 〇〇, lorem, and so on), the tag on placeholder pages for replacing internal material (「差し替え：」), a copyright footer line in the 「© <年> <社名> All rights reserved.」 form under 9pt (including the confidentiality label on the same line; a footer in another form counts as ordinary text under 11pt. Decks whose name contains 「差し替え用」 are checked for neither size, as below), fonts other than Noto Sans JP (Cascadia Mono with only alphanumerics passes), Japanese text in Cascadia Mono (monospace), Japanese periods (「。」) in headings (including mid-sentence ones), and headings that end in 「〜ください」「〜します」「〜しましょう」 (say requests in the lead or body. `deck-writing` → content §6).
- **Wording `要確認` (deck-lint-027, from yomiyasu's lint):** 「動詞を名詞にした語」 (「仕組みの比べ」), 「直訳の語」 (「版」 for version, 「頭」 for head), 「たとえの動詞」 (tools written as people), and 「見出しと箇条の間の読点」 (a comma that only adds a pause after a short topic in a heading or one-line item). Source lines are not checked. How to rewrite them is deck-content-065 in `deck-writing` → content; rewrite who does what, not only the word.
- **`要確認`:** slide text under 11pt (text inside a filled shape: under 9pt [slides-visual-037. Text layered on another shape's fill, such as card body text: under 11pt]. Decks whose name contains 「差し替え用」 keep the original page size, so they are not checked. Whether small text is wrong depends on the page, so it is not `要修正`: keep it only where you can say why, such as supporting text in a dense diagram), empty phrases (such as 「〜を実現する」), fear-mongering phrasing, uppercase English labels (monospace code lines are not counted), missing spaces between Japanese and Latin text, spaces around punctuation marks, leftover 「要確認」 or 「TBD」, confidentiality labels (Internal Only, Confidential, and so on. Those in the footer are combined into 1 finding), 「です・ます」 in slide body text, decks with more than 3 assertive headings (counts headings that contain a Japanese comma (「、」) and end in kana that look like a verb or adjective. Section dividers and the cover are not counted. `deck-writing` → content §4), mixed use of periods across bullets in one frame, numbers on pages without a source line, numbers whose digits are not in the 「出典の表」 (`出典の表にない数字`, deck-lint-026: `slides.py lint` reads the table from the material's folder, the parent of `build/`; off when that folder has neither an outline nor `references.md`), source lines without links, body text over 8 lines (neither counts monospace code boxes. `source:` is not treated as a source line), a heading or lead likely on 2 lines, automatic line breaks likely inside a phrase (it computes the break positions with the same character-width estimate as the build and reports those not at a phrase boundary from BudouX [called separately with `uv run --with budoux`]. It does not count breaks before punctuation or closing brackets that cannot start a line, breaks between alphanumeric words, table cells, footers, paragraphs that are only monospace, or text of unknown size [inherited from placeholders]. Being an estimate, it can be off by one character, so check on the images. Not counted if uv or BudouX is unavailable. slides-visual-013), horizontal arrows not at the vertical center of the boxes on both sides (if there are 2 or more between the same 2 boxes, the offset is intended and is not counted), overflow below the frame, text that reaches the text in the frame below (when a heading frame with a fixed height wraps. slides-lint-025), grids made of lines (3 or more vertical lines with the same top and length. Thin rectangles count as lines. Arrows and lines inside a group of rounded enclosures are not counted. Use a table), empty space below the body (1.0 in or more down to the conclusion band or 6.60 in), boxes larger than their content (0.6 in or more of a filled box below its text. Shapes without text, such as the components that make rounded corners or frame lines, do not count as content), holes in the middle of the body (0.65 in or more between elements or above the conclusion band, 1.0 in or more above the body. Below tables is not counted), large paragraphs of only a number (28pt or more with no unit), misaligned top or bottom edges of white cards in adjacent columns (0.03–1.0 in), Google's default dotted rounded rectangle with round corners (its curvature does not match the cards inside. In JSON, `box` with `"shape": "round_rectangle"` and `"dash": true`), conclusion bands taller than one third of the body, decks whose first page is not a cover (navy background), decks of more than 12 pages without section dividers (navy background), and chapters with only 1 page (or none) after the section divider.
- **Estimated and confirmed:** Findings derived from estimates of character width and line height (a heading or lead on 2 lines, body text over 8 lines, 「見出しと箇条の間の読点」 (it holds only for paragraphs estimated to fit on one line), a line break inside a phrase, overlapping text that overflows its frame, empty space below the body, inside a box, or in the middle of the body) are marked 「（見積もり）」 (`ESTIMATE` in `lint.py`). Confirm them on the Google-rendered images. Everything else is fixed by the JSON.
- **Build warnings** (printed by slides.py. The list and how to fix them are in `commands.md`): check them one by one, like `要確認`.
- **Distribution of font sizes**, and **color pairs below the contrast threshold** (4.5:1 for regular text under 18pt and bold under 11pt; 3:1 for 18pt and up and bold 11pt and up. The fill under the text is used as the background. Text on images is not checked).
- Document rules (Google Docs) are in `google-docs` → lint. The text rules (from emoji to leftover 「要確認」) are shared with slides.
- The Japanese language tag (`ja-JP`) cannot be set with the Slides API, so it is not counted (api.md).
- **Log:** `gslides.py check` and `docs.py check` write the `要確認` to `.desk/lint_runs.jsonl`, one line per run (no text from the material, only hashes of the findings). `python3 lint.py --stats` prints, per rule, how many findings appeared and how many remained until the last check of that material (used in step 5 of `desk-dreaming` → running).

## Japanese check (slides.py wording, then gslides.py wording)

[slides-lint-035] **Check the Japanese on the page JSON once it is written, fix it there, and check again; at the end, confirm separately that the saved deck holds the checked text.** Writing-time rules (deck-content-065 in `deck-writing`) and the review do not close the wording findings: by the run log, 56–68% of the yomiyasu findings stayed until the last check of a material, and only 15 of them were ever judged in a review table (2026-11-04 in `docs/decisions.md`). So the check is a loop of its own with its own record, run on the finished manuscript (the page JSON), where every finding points to the file and JSON key you edit. It needs no upload, no read of the saved deck, and no images, so you can fix and check again as often as you need. Two facts are kept apart: 「点検」 (the Japanese of the JSON is checked) and 「保存した資料との照合」 (the built deck holds that text and its images were looked at). Only both together let you deliver.

```sh
cd <folder>/build
python3 $K/slides.py wording                 # the Japanese check on deck.json (or pages.py). exit 1 until 「済み」. Writes <folder>/wording.json
python3 $K/wording.py keep <folder> <W…> … --why <reason>   # keep a finding unchanged (a proper noun, an established term, a comma that prevents misreading)
python3 $K/wording.py ask  <folder> <W…|R…> … --why <question>  # leave it to the user (goes into the questions at delivery)
python3 $K/wording.py ok   <folder> <R…> … --why <reason>   # a meaning risk that you checked and that is intended (e.g. a number corrected to the 「出典の表」)
python3 $K/wording.py <folder>               # both states, without Google
# after 「済み」: slides.py build <URL>, gslides.py check <URL> (look at the images), then
python3 $K/gslides.py wording <URL>          # the separate final gate: the saved deck against the checked text. exit 1 until 「済み」
```

- **What it reads:** the deck that `slides.py build` would send, made the same way (the pages that `deck.json` lists, or that `pages.py` makes; a JSON file in `build/` that the deck does not list is not read, even with the same name in another folder), turned into the `presentations.get` form without Google (`local_json`), and the same text the lint's wording rules read in it (headings, leads, body paragraphs, cards, table cells, labels in diagrams), and the speaker notes that build would write (`speakerNotes`, or `d.note` in pages.py; a page without them has none), one paragraph or note line at a time. Not read: the footer, monospace code, source lines, text without Japanese, URLs, and anything inside 「」『』“” (quotes, on-screen strings, names of sections), because those are copied, not written. The theme comes from the theme file, as for `slides.py lint`, so Google is not read; only a deck whose theme has no file (`slides.py wording <URL>`) reads the masters of the deck at the URL.
- **Rules (deck-lint-028 in `wording.py`):** the four yomiyasu rules of the lint (deck-lint-027 in "What lint.py does" above) and the Japanese text rules of `textlint.py` (「空疎な言い回し」, 「あおり」, 「和欧間のスペース抜け」, 「約物の前後のスペース」). The notes are spoken, so only the yomiyasu rules (without 「見出しと箇条の間の読点」) apply to them. Each finding says how it is fixed: 〔表記〕 is mechanical (change the spacing, not the words), 〔区切り〕 is a comma, and 〔書き換え〕 needs a rewrite that keeps the meaning.
- **Each finding has a place:** an ID (`W` and 8 hex digits, the same for the same rule and text in every run), the page, and `build/<file> <JSON path>` (the file that `deck.json` listed for the page, then the string in it; a text a component made from numbers and units shows the file only; `pages.py <line>` for pages.py decks). Fix it there and run `slides.py wording` again; run `slides.py lint` on the changed pages too, because a rewrite can add a line.
- **How to fix:** rewrite who does what (deck-content-065), and keep the claim, numbers, conditions, negation, certainty, quotes, proper nouns, code, and URLs. If the only rewrite changes what the page says, do not rewrite; `ask`. Do not rewrite to make a finding go away when the text is right; `keep` it with the reason. A finding is a candidate, not an error.
- **Meaning risks after a fix:** each run compares the text with the accepted text: the text of the first run (even when that run does not pass, so that nothing written after it goes uncompared), moved forward only by a run with no reason not to pass whose risks are all `ok`ed. An `ask` keeps the risk and the comparison until you `ok` it or revert. Each run lists `R…` risks with the same places: changed numbers, URLs, code, Latin words (product and company names), text in 「」, the count of negations, a word with its particle (「A 社が」→「B 社が」), and yomiyasu_diff's meaning risks (certainty, ability, sentence type). A text whose 〔書き換え〕 finding went away (rewritten, deleted, or its notes key removed) also gets a 「書き換えた文を読み比べる」 risk, because a rewrite can keep every protected word and still change the point, the strength of a promise, or an idiom (an independent editor review found 3 such pairs among 15 that changed meaning; 2026-11-04): read the two and `ok` it only if it says the same thing as strongly. Revert the change, or `ok` it with the reason. A risk stays until then, even if you edit the same text again, because the comparison is with the accepted text, not with the previous run.
- **「済み」 for the check** means: no finding without a decision, no risk unchecked, and no text that could not be checked. `ask` items are closed for the check and go into the questions at delivery.
- **Decisions follow the text.** `keep`, `ask`, and `ok` are tied to the hash of the text they were made on, and each run keeps only the decisions for its current findings and risks. When that text changes, the decision is gone and the finding is open again (also if you change it back), because a reason given for one wording does not hold for another (as an approval is dismissed when new commits are pushed).
- **At most 2 rewrites** (`MAX_ROUNDS`): after 2 runs in which you rewrote a text with an open finding, close the rest with `keep` or `ask` instead of rewriting again (yomiyasu's own procedure fixes once and checks again, and does not keep rephrasing to clear warnings).
- **The final gate, `gslides.py wording <URL>`,** checks nothing new in the Japanese; it reads the saved deck (`presentations.get`) and collects its text and notes the same way, and passes only if: the check is 「済み」 and no file it read has changed since; every saved text and note line equals a checked one, page by page (a difference is listed with the page and, for a checked text, its file and JSON path: the deck was edited in the UI, or the JSON was checked but not built); the deck is the revision `slides.py build` made; every page has an image taken by `gslides.py check` after it was built; and `slides.py plan` finds no unbuilt edit (pages, order, theme, or notes, its `notes`). When it fails, fix the cause (copy a UI edit into the JSON and run `slides.py wording`, build, check), then run it again. A passed check does not mean the material is delivered.
- **The record** is `<folder>/wording.json` (written only by `wording.py`): the check (`last`, with the files it read, the inputs of the build) and the final gate (`saved`). `flow.py` of `deck-workflow` shows both under step 10: 「未実施」; 「古い」 when a file the check read changed or went away (a page added to `deck.json` changes `deck.json`), and, for the gate, also when the check was run again after it; 「通らない」 with the gate's reasons. None of them counts as 「済み」.
- The check took 0.12 s on the 18 sample pages (250 texts) without Google (2026-11-04); over 66 saved decks, the check itself had a median of 0.13 s per 30 pages.
