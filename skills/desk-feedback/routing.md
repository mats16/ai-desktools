# Editing rules (routing corrections and verifying rules)

Open this when you receive a correction from the user and when you add or change a rule. How to record a correction and route it on the spot is in "Steps" in [SKILL.md](SKILL.md). This file covers where to route it and how to verify it. Misses are picked up every day by the periodic cleanup (`desk-dreaming`) from the conversation logs, which proposes rule changes with a recommendation (they go in when the user replies; among cleanups of overlaps and stale text, those that only delete a whole rule are applied first and then reported).

## Workspace rules

[deck-rules-001] Rules have no layers. Plugin rules act through the skills and lint: a skill is read whenever it is called, and the workspace cannot turn off a lint `要修正`. Workspace rules (the recipes in `recipes/` and a customer's `memory.md`) are shown where they apply, and you apply the ones that fit the material, the way Claude Code shows a file in `.claude/rules/` for the paths it names. When a workspace rule conflicts with the plugin, the workspace wins. When two workspace rules conflict, the narrower one wins: the customer's memory, then a recipe whose `description` narrows the material (a scene, a material type, slides only), then a recipe for every material. If they are equally narrow, ask the user instead of guessing, record the answer with `--decided`, and leave merging the two to desk-dreaming. What the user says in the current conversation is newer than any file, so it wins; route it back ("Routing corrections" below). File as Issues only what should be fixed upstream (the plugin); the owner fixes it from the Issue. The plugin keeps no workspace file that every conversation reads. An `AGENTS.md` or `CLAUDE.md` the owner writes is theirs, and the plugin neither reads it nor routes corrections to it, because agents load it into every conversation with more weight than a skill, and a rule there applies to work it was not written for.

| Location | Content | Who changes it |
|---|---|---|
| Recipes: `recipes/<name>/RECIPE.md` (frontmatter below) and the files in its folder | The workspace's rules for making materials and gathering, with the templates and checks they use | The making conversation routes corrections on the spot. desk-dreaming proposes with a recommendation (`ledger.py propose`; `apply` on the user's reply; among cleanups of overlaps and stale text, those that only delete a whole rule are applied with `propose --auto` and then reported). The history is kept in the rule ledger (`.desk/ledger.jsonl`): the findings linked to the file, and each change of the file as a version ("Routing corrections" below). If the workspace is under git, also commit |
| `Customers/<customer>/memory.md` | Per-customer preferences ("Customer memory" below) | The same |
| Plugin `skills/` (this folder, etc.; the installed location is read-only) | Rules, checks, scripts, and templates that are the same for everyone | Verify on past materials with the `desk-kaizen` skill, then file an Issue (the owner does the same). The owner fixes it from the Issue, and it arrives via `update` |

**A recipe** is a folder under `recipes/` with a `RECIPE.md` whose frontmatter has `description`. Only `RECIPE.md` is shown as rules; the other files in its folder (document templates under `templates/`, `checks.py`, images) are its resources, listed by name after it. A folder without `RECIPE.md` only groups recipes (`recipes/customer/cxo/RECIPE.md`). How to divide, name, and word recipes, and how to regroup them: `recipes.md`.

```markdown
---
description: 製品のアップデートをまとめる資料で、顧客に効くものを選んで説明するとき
targets: [slides, docs]
audience: [顧客向け]
per_material: true
---
```

- `description` (required): when the recipe applies, written so that it can be chosen from this line alone.
- `targets`: `slides`, `docs`, `vids`. `audience`: the material types of deck-content-039 (`顧客向け`, `社内向け`, `コミュニティ向け`). Omit either for all.
- `per_material: true`: chosen per material (a scene such as summarizing product updates, a material type). Without it, the recipe is shown by the step of the work:
- `step`: omit it for rules about the material itself, which every step of making needs (writing, building, reviewing). `step: gather` for knowledge used only while gathering, including plain research; `step: build` for knowledge used only while building (where logos come from, a theme procedure, an API pitfall). Which plugin files count as which step is `TRIGGERS` in `../../lib/desk.py`, so nobody writing a recipe needs to know the plugin's files.
- Up to 3,800 characters per `RECIPE.md` (`RULE_MAX` in `../../lib/desk.py`), so that the first recipe fits whole, with its heading and the note naming the recipes that did not fit, in the half the hook gives the rules when it shows a customer's memory beside them. Open the recipes the note names yourself. `ledger.py apply` stops proposals that grow a recipe past it, drop its `description`, write an unknown `step`, or write the earlier `paths`; desk-doctor lists recipes over it, unknown values, recipes in a folder named after a skill, and `.md` files under `recipes/` that are not recipes.

**How the recipes reach the conversation,** so that `recipes/` is not forgotten. The plugin hook (`hooks/rules_overlay.py`; Claude Code: Read, Bash, Skill; Codex: Bash; pi: read, bash) shows each recipe once while it is still in the context, and again after compaction removes it. In environments where it does not appear (a host without hooks), open the recipes yourself.
- **Without `step`:** shown at every step of making a material: when you open a file of the making skills (`deck-workflow`, `deck-writing`, `deck-design`, `deck-review`, `slides-build`, `docs-build`, `vids-build`, `vids-voice`, and `desk-feedback` → classifying corrections and routing), and when you open a material's `構成案*.md`, `社内メモ_*.md`, or `references.md` (child agents that write pages or review read the outline). A skill invoked by command (`/desk-tools:<skill>`, `$desk-tools:<skill>`, pi's `/skill:<name>`) counts as opening its `SKILL.md`.
- **`step: gather`:** shown when you open `deck-workflow` → gathering materials, research requests, or steps 1–5, a file of `customer-profile`, `desk-crawl`, or `desk-research`, and also during plain research: a command or read that touches the workspace's `Research/` or `references_index.md` and names a `.md` file (as the template's `grep -rln <word> Research/ references_index.md` does), because Claude Code and pi wake the hook only for `.md`.
- **`step: build`:** shown when you open a file of `slides-build`, `docs-build`, `vids-build`, or `vids-voice`, `deck-design` → slides or documents, or `deck-workflow` → steps 6–8 for decks, the page-writing prompt, or reusing internal decks.
- **`per_material: true`:** in step 5 of `deck-workflow` → steps 1–5, choose those whose `description`, `targets`, and `audience` fit the material, write them at the top of the outline as `- **使う決まり:** recipes/a/RECIPE.md、recipes/b/RECIPE.md` (「なし」 when none fits), and open the outline again. The hook lists these recipes when you open `deck-workflow` → steps 1–5 and when you open an outline without that line, or whose line names something that is not a recipe (renamed, deleted, or without `description`); until the line is fixed, each open of the outline also shows a note naming them. Once the line is there, every time you open the material's `構成案*.md`, `社内メモ_*.md`, or `references.md`, the hook shows the chosen recipes first, together with the customer's memory (customer-facing and internal materials alike).
- **A workspace from before 2026-10-29** (`rules/<name>.md`, or `rules/<skill>/<file>.md`): the hook no longer shows them, and notes at the start of a material to move them with `desk-migrate`.

- **Do not rewrite the plugin's installed location (`~/.claude/plugins/cache/…` etc.).** Reinstalling erases the changes.
- **Grow checks in the workspace too.** Rules a machine can check go first into a `checks.py` in the folder of the recipe they enforce, with `slides(p, r)` for slides and `doc(doc, r)` for documents (lint loads every `checks.py` under `recipes/` every time; how to write them: `recipes/README.md`). Once it is clear that they help other people too, file an Issue to move them into the plugin's lint (`lint.py` of `slides-build`, `doc_lint.py` of `docs-build`, or `lib/textlint.py` for rules shared by both).
- **Promoting to the plugin.** Workspace rules and checks that help other people too (not that person's taste or a customer's circumstances) become a 「プラグインに上げる」 proposal from desk-dreaming. Apply it with the `desk-kaizen` skill (clone the original repository, fix it, compare before and after on past materials, and file an Issue with the reason, the background, the verification results, images if it is visual, and the diff of the proposed change). When the owner's fix arrives, delete the copy in the workspace's recipe.
- The results of re-researching with `desk-research` (its sources and the fixes to the skills that reflect it) are plugin knowledge, so file them as Issues with `desk-kaizen`. The logs and `state.md` stay in the workspace's `Research/deck_research/`.

## Customer memory

[deck-rules-005] Preferences per customer are kept not as rules but as memory in `Customers/<customer>/memory.md`. Rules (`recipes/`) take the form 「〜のときは〜する」, apply to every material their file covers (a recipe: the materials its `description` names), and are verified by lint or review. Memory is what applies across materials about that customer's audience (honorifics, the tone of the language, the audience's position and interests, past decisions and rejected proposals); use it as a premise when making a material and check against it in review. Who the customer is (business, organization, products in use and their setup, engineers' preferences) goes not in memory but in the customer's `profile.md`, with sources and dates (the `customer-profile` skill). When unsure, separate by the form of the sentence. 「〜である」 (a fact: 「エンジニアは Terraform で全部管理している」) goes in the profile; 「〜にする・しない」 (an instruction: 「Terraform のコード例を入れる」) goes in memory. For an instruction decided from a fact, write the fact in the profile and the instruction in memory.

- **Format:** one item per line, without an ID ("Workspace rules have no IDs" below). As with rules, the date and the original wording go in the ledger (`ledger.py add --to Customers/<customer>/memory.md`). It is read every time, so keep it short.
- **When it appears:** when you open that customer's `構成案*.md`, `社内メモ_*.md`, or `references.md`, the plugin hook then shows it (Claude Code, Codex, pi). In environments where it does not appear, open it yourself. It takes precedence over the workspace rules and the plugin.
- **What not to put in:** personal names, spend amounts, internal-only assessments. Write them in `社内メモ_*.md` so they do not slip into customer-facing materials. Things only for that material (the wording on this page) get `--to 戻さない`.
- **Going stale:** it stops holding when the person in charge or the organization changes. If it conflicts with the user's newer words, update it to the newer one (the earlier date: `ledger.py why Customers/<customer>/memory.md`). If you cannot tell which one is current, ask.
- **Generalizing:** if preferences with the same gist are in the memory of two or more companies, move them into a recipe as a rule independent of the customer (c of step 4 in `desk-dreaming` → running, written in its propose prompt). Do not promote directly from memory to the plugin.

## Routing corrections

Record findings in the workspace's rule ledger (`.desk/ledger.jsonl`) with [../../lib/ledger.py](../../lib/ledger.py). Do not create a 「修正の指示」 section in the outline. Before editing a recipe (on the spot, or when the user asks to edit rules directly), open `recipes.md` and write as it says, so a rule written in a conversation reads the same as one written by desk-dreaming (deck-rules-009). In the rule text, write only the rule and a short reason; the date, the user's words, which material, and whether the user decided it go in the ledger, linked to the rule file (`ledger.py why <file>` shows them). The ledger contains customer information, so do not copy it outside `.desk/` (Issues, PRs, chat).

```sh
L=<plugin>/lib/ledger.py
python3 $L add --deck <material folder> --quote "<the user's words (verbatim where possible)>" --fix "<what was fixed>" --to <destination> --check <lint・レビュー・なし> [--decided] [--plan <AI・人>]
python3 $L list --deck <material folder>     # findings for that material. With --open, only those whose destination is 「未」
python3 $L route <c-ID> <destination>        # the destination was decided or changed (edit the rule file first)
python3 $L why <file>                        # the findings, review results, and versions of a rule file
```

- `--to` is one of: a workspace rule file (`recipes/<name>/RECIPE.md`, `Customers/<customer>/memory.md`, `recipes/<name>/checks.py`), a plugin rule ID (`slides-visual-012`), a plugin file (for a plugin rule without an ID), `戻さない`, or `未`. `add` and `route` refuse anything else (an ID and a file side by side, 「この資料」, 「戻さない（理由）」), because such a destination does not link to the rule: `why`, `candidates`, and `effects` miss it, and a rule the user decided loses its protection. Put the reason in `--fix`.
- `--decided` marks what the user clearly decided (chose from proposals, or stated 「〜にする」 outright). desk-dreaming puts statements that conflict with it on hold for a decision and does not overturn it. Plugin rules are defaults and may be overridden in the workspace.
- `--plan` marks a structure miss. Attach it to findings after the plan review (§5 in `deck-workflow` → the flow) that changed the audience, the question, the claim, or the order and were not raised in that review (for ① AI, not among the findings received at the end of the outline; for ② human, not in what the user said when shown the outline; in both cases, excluding those in the list of questions for the user). The value is the plan review chosen for that material (`AI` or `人`). The outline review does not check against rules, so as not to constrain the maker's ideas, so only its misses are counted here (the weekly table and the last line of `ledger.py rules`; step 5 in `desk-dreaming` → running). If a finding turns out to be a miss after it was added, mark it with `ledger.py plan <c-ID> <AI・人>`. Remove a wrong mark with `plan <c-ID> なし`.
- **Workspace rules have no IDs** (2026-10-27 in `docs/decisions.md`). The ledger keeps the history instead, by the IDs of findings (`c-`) and of versions (`P`).
  - **Edit the file, then write the destination.** `ledger.py add --to <file>` and `route <c-ID> <file>` compare the file with its last version in the ledger and, if it changed, record a version (the whole text before and after, and the finding it took in). Writing the destination before editing leaves the edit unrecorded.
  - **Changes made outside the ledger** (by hand, or by a conversation that did not write the destination) are found by `ledger.py drift` and recorded by `drift --record` as 「手で直した」. They are treated as the user's edits and not overturned. A file with no version yet becomes 「初めの版」 (also when its first destination is written), because the ledger cannot tell its earlier text; that version cannot be undone.
  - **desk-dreaming rewrites a file only through a proposal** (`propose --rewrite`; step 4j in `desk-dreaming` → running), so each rewrite is a version too, with the change per finding (`--changes`).
  - **Pointing at a plugin rule** from a workspace rule: write the ID without brackets (「slides-visual-012 より優先」). `ledger.py apply` stops a proposal that writes a bracketed ID into a workspace file.
  - A workspace from before 2026-10-27 still has `[ws-…]` IDs. desk-migrate removes them and links their findings to the files they were in (`desk-migrate`).
- **Plugin rule IDs:** one per item, with `[<area>-<topic>-<3 digits>]` at the head of the line (e.g. `- [slides-visual-<number>] 収まらない表は 2 枚に分ける（文字を小さくすると読めなくなる）。`). A new one comes from `ledger.py next <prefix>` (desk-dreaming's proposals to the plugin, and desk-kaizen). The ID says what the rule is about, not where it is written, because the ledger links each rule's corrections, recurrences, and review results by ID, and a changed ID cuts that history. The area is `deck` (common to slides and documents), `slides`, `docs`, `vids`, or `desk` (the mechanism as a whole, such as the scheduled cleanup); the topic comes from the list printed by `ledger.py topics` (`TOPICS` in `../../lib/ledger.py`), with a language suffix only where a topic is split by language (`vids-voice-ja`). To find where a rule is written, run `ledger.py where <ID>`.
  - **Never change an ID once given.** Keep it when the rule moves to another file or skill, when files are split or renamed, and when its scope grows (a slides rule that now also applies to documents keeps its `slides-` ID; say so in the text). An area or topic is renamed only when the user decides it, with a dated map in `desk-migrate` that rewrites the ledger too, so the history stays linked (`factory-dreaming` → `desk-dreaming` on 2026-10-25).
  - **Splitting and merging:** when one rule becomes two, the original keeps the ID and the new one gets the next number (`ledger.py next <prefix>`). When two become one, keep one ID and route the other's corrections to it (`ledger.py route`).
  - **Do not reuse numbers,** even of deleted rules (`ledger.py next` counts the ledger too).
  - **A new topic** is added to `TOPICS` before use; `ledger.py next` refuses prefixes not in it, and the selftest fails on plugin IDs outside it (so typos and drifting topics are caught). Do not name a topic after a skill or a file (`slides-build`, `pages`), so an ID is not read as a location.
  - **How a rule is checked is not part of the ID** (rules move from review to lint over time). Say it in the rule text (「lint が〜」), and have the lint check name the rule ID it enforces.
  - When referring to a rule from other text, write `slides-visual-012` without brackets (a bracketed ID is read as the place where that rule is written; `ledger.py`).

- **Merge them and put them in the form of rules.** Merge items with the same gist and rewrite them as rules of the form 「〜のときは〜する」. Fixes only to this material's content (the wording on this page, replacing a number) get `--to 戻さない`.
- **Destination:** route to the workspace ("Workspace rules" above). Rules go in a recipe, including those that seem to need every conversation (handling confidential information, folders, research): a recipe without `step` is shown in every step of the work, and one with `step: gather` also in research requests. Open `recipes.md` first, and add to the recipe whose `description` covers it. If none does, create one (`recipes/<name>/RECIPE.md`, a name in lowercase English after its purpose, such as `recipes/product_update/`). For a rule that holds only for some materials (a scene, a material type), use a material recipe (`per_material: true`) and add it to 「使う決まり」 in the current outline. When you want to change a plugin rule, also write it in a recipe, adding the ID of the rule it overrides in the form `- 〜は〜にする（slides-visual-012 より優先。<短い理由>）。` (desk-dreaming uses `ledger.py candidates` to see the number of overrides and stale overrides of rules removed from the plugin). When overriding a section without an ID, write 「プラグインの〇〇の節より優先」.
  - Workflow steps and what to keep: `deck-workflow`
  - Structure, wording, 「文体」, and how to write sources: `deck-writing` → content; what changes by material type: `deck-writing` → customer-facing materials, internal materials, explaining materials
  - Visuals: `deck-design` → slides (decks), `deck-design` → documents (documents)
  - Reuse: `deck-workflow` → reusing internal decks
  - Sources and the ledger: `deck-workflow` → gathering materials
  - Building with the Slides API: `slides-build` (writing pages, diagrams, commands, themes, images, Slides API pitfalls, older decks)
  - Building with the Docs API, and checking and delivering documents: `docs-build`
  - Checking and delivery: `slides-build` and `deck-review` (asking, verifying and fixing findings, splitting fixes; the review aspects are in the slides review prompt and the documents review prompt)
  - How to edit these rules: this file
  - Per-customer preferences: the customer's `memory.md` ("Customer memory" above)
  - About the customer (business, setup, engineers' preferences): the customer's `profile.md` (`customer-profile`)

  Also decide how to verify it ("Verifying rules" below).
- **Ask before routing:** items that conflict with the current rules, and items where you cannot tell whether they are just for this material or should become a rule. Set `--to 未` and ask in the report.
- **Record and report.** After editing the rule file, set the destination to that file (or the plugin rule ID) with `ledger.py route`. At the end of the report, write which correction was routed to which rule (`ledger.py list --deck <material folder>`).

## Verifying rules

[deck-rules-002] Rules are followed when making a material and verified with the same rules at the finish. Decide how to verify a rule before adding more considerations. When adding a rule, also decide which of the following verifies it.

| Method | What it looks at | How to write it |
|---|---|---|
| lint | Things countable in JSON (font size, font, character count, position, page order). Positions that JSON cannot estimate (line wrapping, page breaks, padding inside boxes) are measured on the images Google renders (`box_pad.py`, `doc_layout.py`) | Say in the rule text that lint checks it (「lint が〜」 in a Japanese rule, "lint flags …" in an English rule) and add the check to the `checks.py` of the recipe (when promoting upstream, move it to `lint.py` and `--selftest`). Add it the first time; do not wait for a recurrence |
| Review | What AI judges from images, text, the outline, and the rule text (the storyline, the impression of the wording, the meaning of diagrams, how margins and density look) | No tag (rules that do not say lint checks them are checked in review). Check which of aspects 1–5 in the `deck-review` request texts (decks: the slides review prompt; documents: the documents review prompt) covers it; if none does, add it to an aspect |
| Principle | The axes in `deck-writing` and `deck-design` | Do not make it a condition. Use it as the basis for review questions |

- [deck-rules-003] **Do not force what cannot be counted into lint.** It leads to writing just to pass lint (「禁句をほかの空疎な語に置き換えるだけにしない」 in `deck-writing` → content §6). Do not remove the places where AI judges by looking at images and the rule text.
- [deck-rules-004] **Do not force a good-or-bad binary.** For a lint `要確認`, either fix it or state why it stays. In review, things the rules do not decide, things that can be read either way, and things whose fix would change the point become 「聞く」, and are returned to the user with the reason for hesitating and proposals ("What to fix" in `deck-review` → verifying and fixing findings).
- **Fix or remove conditions with many false hits.** Rules whose `要確認` always end as 「残した」 (`lint.py --stats`), and conditions that missed something the user fixed after the check passed, are reviewed in step 5 in `desk-dreaming` → running.
- **Count how well rules work.** The rule ledger counts, per plugin rule and per workspace rule file (a recipe, a memory), findings raised even though a plugin rule exists (recurrences; not counted for files, which hold many rules) and the results of rows in the deck-review findings table with the rule column filled in (「直した・残した（誤り）・聞く」) (`ledger.py rules`, `why <ID or file>`). A rule with continuing recurrences and 「直した」 is not being followed when making, so push it down into a check or a making step. A rule with continuing 「残した（誤り）」 needs rewording. A rule that produces no findings may simply be followed, so do not remove it for that reason alone. The next move per rule or file (push down, rewrite, add a condition, delete the copy, revisit the override) is printed by `ledger.py candidates`. `ledger.py trace` puts each plugin rule's edges in one table (the scripts that name it, the files that point to it, the decisions, the ledger counts), first the rules pushed down by the counts that no script names yet. Whether a workspace rule helps other people too is not counted per file (every customer's findings reach a general file); desk-dreaming judges it per finding when it rewrites the file (4i in `desk-dreaming` → running). A rule that was applied or merged has not been shown to work: `ledger.py add` and `ledger.py review` record which harness (plugin and workspace rules) each material was made with, and `ledger.py effects` compares the materials made before and after each plugin rule's text, or each workspace file's version, changed (step 5 in `desk-dreaming` → running).
