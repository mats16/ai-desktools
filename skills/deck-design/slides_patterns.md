# Visual: tables and charts, diagram patterns, habits of AI-made materials (slides, §5–8)

The second half of [slides.md](slides.md) (§1–4: this folder's style, text, color, shapes). The section numbers continue from there, so 「slides §6」 in other skills means §6 here. Read slides.md first.

## 5. Tables and charts

- [slides-visual-054] Remove vertical rules from tables and keep horizontal rules to a minimum (only for tables where the borders of merged cells are hard to see, draw both with JSON `"borders": "grid"`). When there are many rows, use `EEEDE9` on alternate rows. To enclose a column or a cell for emphasis, use a red 2pt rounded rectangle (§4; how much to emphasize is in `SKILL.md`). By default JSON `table` (and `d.table` in pages.py) makes the header row white bold on navy, the first column navy bold, and alternate rows `PANEL` (`first_col` and `zebra` turn these off).
- Build tables with JSON `table` (`d.table` in pages.py) (it sets the font and text size per cell). If only the text inside a figure or table has a different font, the layout breaks there (AI 実践 1-2; lint stops fonts other than Noto Sans JP).
- [slides-visual-055] Single-series charts have no legend; write labels directly near the series. Charts with 2+ series (JSON `bars` with `series`) have one legend row above the chart, because grouped and stacked bars have no room for names near each series. Keep it at the top of every chart, so readers find it in the same place in every material. Use 3–5 gridlines. No 3D, shadows, or gradients. Take series colors from the §1 table (見た目 1-12). JSON `bars` draws bars in this form (`build-slides` → diagrams). When one bar is emphasized (`hot`), the others are gray, because emphasis is relative and navy beside red competes with it. For a rate or a score, set the full scale (`max`: 100 for a rate), because the length then shows the share and the room left shows what is missing. A line laid over bars (a quantity in different units) is gray, and a straight line for a target or limit is a red dashed line; next to each line, write its value and what the line is. When you lay both over, hold back the emphasized bar (`hot`) so there are not two reds. Draw numbers that are not final (a month in progress, an estimate, a forecast) as dashed-outline bars (`tentative`), not as solid bars, because a solid bar for a partial month reads as a real drop.

## 6. Diagram patterns

Choose the pattern from the one sentence you want to say, and use one pattern per page. Write the pattern for each page in the outline (見た目 1-13. The primary source of the pattern names is unconfirmed).

How to choose the body's form for each page, and what to keep the same across pages, are slides-visual-048 and slides-visual-049 in `SKILL.md`.

| What you want to say | Pattern | Diagram convention |
|---|---|---|
| There are three X | Parallel | Line up boxes of the same size. Same size means peer status |
| X and Y differ | Contrast | Place them left and right, and align the axes of comparison |
| It proceeds in the order X | Transition | Left to right, or top to bottom. Arrows show order |
| It is made up of X | Structure | Stacked or nested. Enclosures show groups |
| It repeats X | Cycle | A ring. Show where it starts. On a wide slide, put the stages on the orbit of a lightly filled ellipse, and show direction with arrowheads on the orbit between stages (the bullet below) |
| It splits into X | Hierarchy | A tree |

- [slides-visual-026] Align the main flow of a diagram (data or user actions) top to bottom or left to right. Things outside the main flow (such as the owner writing and maintaining the repository) may go in reverse or loop around. What matters is that what the page wants to say matches the diagram's main flow. If arrows point every which way and the main flow cannot be read, first align the direction of the main-flow arrows.
- [slides-visual-041] Do not lay out different kinds of flow in one diagram (such as the flow that obtains an authentication token and the connection that reads and writes data) in parallel in the same direction. Separate them by direction (vertical and horizontal) or by line style, and number the order (the numbers on the arrows, slides-visual-056). Do not draw components that the page's claim does not need; move them to the page that talks about them.
- [slides-visual-043] Place boxes in a flow diagram so that arrows can be drawn straight. Use bent lines (JSON `"route": "bent"`) only when branching from one box or merging into one, and do not bend a single flow to route around other boxes. If you want to bend it, re-place the two boxes it connects in the same row or the same column. A bent line makes it hard to read where the flow goes from and to, and people ask why it is bent. The build warns (arrows with sides written are left alone, because they are used for return lines).
- [slides-visual-056] **When a flow has more steps than words that fit on its lines, number the arrows and explain the numbers below the diagram.** Put a small circle with the step number on each arrow of the order, in the line's color (JSON arrow `num`), and below the diagram write one line per number, in order, with circles of the same color and size (a `list` with `size` and `fill`). This is the numbered callout of cloud reference architecture diagrams (such as AWS's): the diagram stays readable at a glance, the reader follows the order by the numbers, and the speaker can point to 「3」. Words written on every line crowd the diagram and run into other lines and boxes. When the steps are few and their words are short enough for the lines (about 10 characters), write the words on the lines (`label`) instead, because a legend makes the reader look back and forth. Number only the arrows that are part of the order (slides-visual-020). An arrow outside the order (such as fetching a token on the side) gets a `label` or a dashed line, not a number. Keep the colors of the circles to the colors the lines already have, so the numbers add no new color to the page (§3).
- [slides-visual-029] **In a cycle, do not connect stages with straight arrows.** Connecting boxes on a ring with straight lines forces a circle to be traced. Place one ellipse with a light fill (`PANEL`) and a thin outline (`SUB`), put the stage boxes on its outline, and place short arrowheads, pointing along the outline's tangent, on the outline between stages. Inside the ring you can put one or two lines on what happens in one round. Check this in review aspect 5.
- [slides-visual-030] On customer case study pages, place that company's logo instead of the company name in text. It shows at a glance which company the story is about, and it looks good. For how to get logos, see `build-slides` → images. When you line up several companies, equalize the heights by visual weight (wide logos lower, logos with a large mark taller).
- [slides-visual-031] 考え方を説明する図（「製品 A・B」のような一般名の対比）も、顧客向けなら聞き手のいまの構成（部門、使っている製品、データの入れ方と使い方）に当てはめて描く。左にいまの姿、右に考え方を当てはめた姿を置くと、聞き手が自分の話として読める。いまの姿に置く製品は、アカウントマップ・RFI・顧客の `profile.md`・`memory.md` で確かめ、聞き手が使っている主要なもの（DB なら Oracle など）を漏らさない。漏れると「分かっていない」と読まれる。逆に、聞き手がしていない連携（例: 基幹へのリバース ETL）を、一般論の流れとして描かない。描くのは聞き手の痛みのある流れ（例: 基幹からの取り込み）で、それが提案の狙いにつながるようにする。聞き手の構成で確かめていないところは図に書かず、聞き手への問いかけとして `authorNotes` に残す。当てはめるときは、言いたいことに要る要素だけを入れる（運用の主体やツールの名前などの細部は入れない）。2 重管理のような状態は、言葉のラベルではなく、同じ部品（データの印など）が 2 か所にあることで見せる。変えたあとの姿の図には、聞き手のいまの資産（Git のリポジトリ、Notion など）がどこで活きるかを部品として入れる。ただし、置き換わる仕組み（内製の ETL など）は、変えたあとの姿に残さない。そこは置き換える機能（「Databricks の機能で取り込む」など）で書くか、ラベルを省く。一方、歴史や一般論を説明する図は、固有の製品名を出さず、使い方（DWH・ETL・AI エージェントなど）で描く。製品名は、聞き手に当てはめるページで出す。
- [slides-visual-032] In diagrams that line up options (paths per cloud, configurations per plan, and so on), when the customer's environment is known, do not leave all options lined up in the general form. Enclose the customer's option in a red (`RED`) rounded rectangle, or remove the irrelevant options. You may keep one row of the reference procedure (such as the procedure in the other party's product help) for comparison. When you are unsure whether you may tell the other party (such as a partner) about the customer's environment, do not quietly fall back to the general form; ask the user. Check this in review aspect 3.
- [slides-visual-033] When you show the current state and the changed state on two pages, draw both with the same skeleton (order of tiers, position and size of boxes, numbers), and change only what changes. When the reader flips the page, the difference (boxes merging into one, a shorter path) shows in the diagram. The same applies to other pages shown in sequence by flipping (a quiz question and its answer, pages that add markers to the same diagram): keep the positions and sizes of the same components. Even when the amount of content differs, keep the box heights equal, and add what grows at the bottom.
- [slides-visual-034] In diagrams that line up columns for contrast or transition, draw the same components in the same tier in every column (example: query engine in the upper tier, data storage in the lower tier). If you drop a component in one column, the diagram no longer shows what happens in that column (where the analysis happens). When you fix things after a finding about the content, reflect it in the diagram too, not only in the wording. Who reads what, who builds what, and who uses it: do not only write it in text; draw it with arrows from builder → result → user.
- [slides-visual-035] When pages comparing the same two things follow one another (OLAP and OLTP, a conventional DB and Lakebase, and so on), keep the left-right order (the column order for tables) the same on every page. Also keep the main side (such as Lakebase) on the same side. Check this in review aspect 2.
- [slides-visual-036] In architecture diagrams (data flows, division of roles, how things connect), do not write only general names like 「データソース」 or 「SIEM」 in the boxes. Write the concrete log types and product names, and add a logo or product icon to products and a line icon (one set, one color) to log types. Add 「（例）」 to concrete names when you do not know whether they apply to the audience's environment. Do not write the connection method in a separate enclosure; add the name of the means (Add-on, HEC, and so on) to the arrow between boxes. Treat small flow diagrams in the Appendix and elsewhere (boxes connected by arrows, like 「ビジネスメンバー → Genie One → Notion」) as architecture diagrams too: put logos in product boxes and line icons in people boxes. Do not make text-only boxes (icons look better). Also treat lineage diagrams (forks, embedding relations) and when-to-use-which diagrams as architecture diagrams: give product and OSS boxes their official logo (Iconify `logos:` or `simple-icons:`, otherwise the GitHub organization's avatar), and give OSS without a logo the logo of the language it is written in or line art. Place images with JSON `image` (or a logo on a marked `card`). Place icons to tell content apart, not to decorate headings or text (§7, "meaningless icons"). For how to make logos and icons, see `build-slides` → images.
- [slides-visual-042] **Do not draw a flow that copies data and a direction that queries without copying with the same solid arrow.** Things where data moves (copy, sync) get a thick solid arrow, with a box for the copy on the receiving side. Things where only queries arrive and data does not move (federation, registering in a catalog and reading) get a dashed arrow (JSON arrow `"dash": true`), drawn in the direction from the querying side, with no data box on the receiving side. Show which is which with a legend or an enclosure (「データを写す」, 「写さずに問い合わせる」). Pages that line up ways of connecting data (integration, sync, registration, federation) use a diagram of paths between storage boxes, not cards.
- [slides-visual-045] Draw the timetable of one run or one piece of work (what was done at which minute) not as a table but as time bars (a Gantt chart: time across, steps or tasks down; write the time divisions in `cols` of JSON `gantt`), and show long segments and segments that matter to the claim with color (`hot` in `status`).

## 7. Habits typical of AI-made materials

In every case, the problem is that they appear as defaults unrelated to the subject (研究 1-8). When you find one, consider whether it helps on that page, and remove it if it does not.

- Secondary labels and descriptions that only restate what the layout shows (slides-visual-047 in §1)
- Emoji, long dashes (—), uppercase English labels (the 「KEY POINTS」 type). lint counts them
- Lines under headings, vertical lines at the slide edge, a line on only one side of a card (the official skill also forbids these)
- Mass-produced rounded cards with shadows, meaningless icons (decorations for nouns), the same pattern on every page
- Neon colors on dark backgrounds, gradients
- 「〜を実現」「シームレス」「次世代」などの空疎な言い回し（`deck-writing` → content の 6）
- 会社名や製品名を替えてもそのまま使える文
- The same decoration on every page. Place the kicker and the conclusion band only on pages that need them, as in §1

## 8. AI design suggestions not to use

As in §1, this folder's style takes priority over the design suggestions AI often makes (the official pptx skill's Design Ideas are the typical case. We do not use that skill for slides, but models tend to make the same suggestions). Specifically, do not use the following (見た目 2 節).

| Official skill | Why not use it |
|---|---|
| Title 36–44pt | One Japanese character is almost twice as wide as a Latin one. At 36pt one line holds about 20 characters, and a claim sentence does not fit. The 24pt in §1 is enough |
| "Images, icons, or diagrams on every slide" | In Japanese materials, decorative icons are a sign of AI-made work. Place a diagram only when the content becomes a diagram |
| Distinguish with shadows; icons in colored circles | Same as above. The panel `EEEDE9` and the rule `DCE0E2` are enough |
| Safe fonts are Arial and Calibri | Japanese uses Noto Sans JP. Latin text also uses the Latin glyphs of the same font, without mixing (only code uses the monospace Cascadia Mono; §2) |
| Bold palettes per subject; avoid cream backgrounds | Fix the palette to the official brand palette in §1. The Oat Light background was chosen as a brand color |
| Large numbers at 60–72pt | For materials meant to be read, 32–40pt is enough |
| Italic accents | Japanese has no italics |
